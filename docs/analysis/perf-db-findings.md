# Производительность конвейера на x10 (задача 2)

**Итог.** Причина найдена и закрыта: дело было не в БД, а в Open Session in View (OSIV). `POST /api/pipeline/run` — HTTP-запрос, а `spring.jpa.open-in-view` по умолчанию включён, поэтому весь прогон шёл в одном `EntityManager`. Каждая пачка `load_ops` (`operationRepository.findAllById`) добавляла 50 сущностей `Operation` в persistence context, и при каждом коммите (`intake`, `claim`, `save`, `map` — четыре на итерацию) Hibernate проверял на изменения **все** накопленные сущности — до 120 000 к концу прогона. Отключение OSIV: **x10 930 с → 104 с** при той же точности.

## Стенд

Одна машина (macOS, Docker Desktop: 6 CPU, 6 ГБ), PostgreSQL 16 в контейнере с `pg_stat_statements` (флаги как в обновлённом `docker-compose.yml`), Java в контейнере в сети PostgreSQL, Python-сервис на хосте. Чистая база перед каждым прогоном: `TRUNCATE operations CASCADE`, `DEMO_OPERATIONS=100000` (+20 000 хаоса = 120 000), справочник 1 млн договоров / 300 тыс. клиентов, настройки NLP версии 1 (порог 0,5), `maxStoredCandidates = 20` (задача 3).
Снимки раз в минуту — `nlp-service/eval/db_monitor.py` (оба SQL из ТЗ, `docker stats`, мс на вызов каждой стадии по приращению `avp_pipeline_stage_seconds` из `/actuator/prometheus`; на 9-й минуте — `EXPLAIN` запроса intake). Данные: `nlp-service/eval/load/x10_diag*`, `x10_e1_osiv_off*`, `x10_final*`.

- Внешние стадии `intake + nlp_batch + map` = 929,5 с = `run_s`.
- **Весь SQL прогона — около 35 с** (сумма топ-15 `pg_stat_statements`, включая сброс демо 2,7 с). Формулировка «БД ≈ 66% времени» в `docs/load-testing.md` неверна: 66% — это стадии, внутри которых есть транзакция, а не время выполнения запросов.
- Стоимость вызова каждой стадии с транзакцией росла одинаково, ≈7–8 мс за минуту (`intake` 42 → 151 мс, `claim` 44 → 153, `save` 50 → 167, `map` 53 → 158), а SQL `enqueue` внутри `intake` всё время стоил 0,2 мс. ### Проверка гипотезы «мёртвые версии строк»

**Опровергнута.**

- `n_dead_tup` `operations` за прогон: 7–19 тыс. на 120 тыс. живых строк; autovacuum прошёл 10 раз (≈раз в 1,5 минуты), `nlp_task` — так же.
- `EXPLAIN (ANALYZE, BUFFERS)` запроса intake на 9-й минуте: `Index Scan using idx_operation_pending`, **1 буфер, 0,018 мс**.
- Долгих транзакций нет: в `pg_stat_activity` только короткие `idle in transaction` (0,01–0,07 с), `backend_xmin` не застревает, autovacuum не блокируется.
- Если бы чтение раздували мёртвые версии, рос бы SQL `enqueue`/`claim`, а он стоил 0,2 мс и ~0,4 мс на всём прогоне.

### Почему `n_live_tup` в `operations` больше 120 000

`n_live_tup` — не счётчик строк, а оценка из последнего autoanalyze/autovacuum. В этом прогоне: 143 271 на 13-й минуте и 159 430 после прогона при `count(*) = 120 000`. После 576 тыс. обновлений таблица выросла до 21 176 страниц (165 МБ), живые строки распределены по страницам неравномерно, и ANALYZE экстраполирует плотность выборки на все страницы — получается завышенная оценка. После полного VACUUM `reltuples` = 120 000. Значение 133 755 у второго разработчика — та же оценка, а не реальное число строк. (Кумулятивные `n_tup_ins` / `n_tup_upd` после `TRUNCATE` не сбрасываются: в них учтены и прошлые прогоны.)

## Что ещё важно

- **Планировщик этим не страдал.** `PipelineScheduler` работает вне HTTP-запроса, OSIV на него не действует — деградация была только у ручного `POST /api/pipeline/run`, а именно им и меряли нагрузку.
- **Риск выключения OSIV.** Ленивые связи сущностей вне транзакции больше не подгрузятся. В REST и сервисах для Vaadin сущности наружу не отдаются (только DTO через JDBC), тесты и оба прогона прошли. Vaadin-экраны тоже должны работать через сервисы с DTO, а не с JPA-сущностями.
- **Цифры с одной машины.** Абсолютные значения на стенде второго разработчика будут другими (там 816 с против 930 здесь), но причина та же: на его данных тоже росли все стадии с транзакцией.
