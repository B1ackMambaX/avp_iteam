# Номера договоров и ИНН на 24 текстах заказчика (задача 5)

Только измерение, парсер не менялся.

## Какой компонент извлекает номер и ИНН

- **Номер договора** — Java, `backend/src/main/java/com/bank/avpiteam/service/mapping/ContractNumberExtractor.java`, `extractNormalized`. Вызывается в маппинге (`MappingService.mapBatch`). Номер ищется только после слов «договор…» или «дог.», между ними допускается до двух слов («по договору поставки № …»); номер должен содержать цифру, допускается буквенный префикс до 4 символов через пробел или дефис. Результат нормализован так же, как `contracts.contract_number_norm`: только буквы и цифры, верхний регистр, Ё → Е.
- **ИНН из текста назначения не извлекает ни один компонент** — ни в Java, ни в `nlp-service`. Маппинг берёт ИНН только из полей операции `sender_inn` и `receiver_inn` (`MappingService`, шаг 1; `MappingJdbcRepository.clientIdsByInn`).

**Как прогнано.** Тексты взяты парсером `customer_examples.py` из `nlp-service/eval/data/customer_examples.txt`; `ContractNumberExtractor.extractNormalized` вызван на скомпилированных классах ветки отдельной программой (`java -cp backend/target/classes CheckFormats.java`), код парсера не менялся. Ожидаемое значение нормализовано тем же правилом и сравнено на равенство.

**Итог: 23 из 24.** Единственный промах — **№ 6**: «Обеспечительный депозит по агентскому **соглашению** № 987654/1». Слово «соглашение» не входит в якоря экстрактора («договор», «дог.»). Номера счетов и отчётов («по счету № FDK19032FK» в 11, «№НЕ-456» в 18, «счет № 654» в 16) не извлекаются — так и задумано.

Замечания:
- Нормализация убирает разделители: `23/А` и `2/3А` дали бы одно значение `23А`. На этих текстах коллизий нет; совпадение номера в маппинге — лишь один признак из нескольких.
- В 16 дата договора записана словами («договор № 567 от десятого августа деветысячи двадцатого года») — на номер это не влияет, он извлекается.

В 4 из 5 случаев ИНН в тексте — это ИНН третьего лица-организации. Именно эти бенефициары не извлекаются `/extract-name` (только персоны, см. `customer-examples-diagnosis.md`, раздел 4), то есть ИНН из текста — единственный идентификатор, по которому их можно было бы связать с договором.

## Признак «ИНН из текста» среди весов маппинга

**Подтверждено: такого признака нет.** Веса — `MappingProperties.Weights` и `application.yml` (`mapping.weights`): `party` (отправитель/получатель — сторона договора, по полям `sender_inn` / `receiver_inn`), `both-sides`, `contract-number`, `beneficiary-name`. Правила — `MatchRule`: `PARTY_SENDER`, `PARTY_RECEIVER`, `BOTH_SIDES`, `CONTRACT_NUMBER`, `BENEFICIARY_NAME`. ИНН из назначения платежа не извлекается и в скоринге не участвует.
