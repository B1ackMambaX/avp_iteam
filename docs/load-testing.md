# Нагрузочное тестирование и мониторинг 
Статус: промежуточный. Нагрузка x1/x2/x3/x10 измерена, главная причина падения скорости на больших объёмах локализована частично (см. «Открытые вопросы»).

## 1. Что сделано

- Данные: демо-генератор + «хаос»-сценарии (только имя+отчество, только отчество+фамилия, непонятные номера договоров).
- Мониторинг: Prometheus + Grafana (дашборд `monitoring/grafana/dashboards/avp_iteam.json`), метрики Java и Python.
- Метрики стадий конвейера `avp_pipeline_stage_seconds{stage}`: `intake`, `enqueue`, `nlp_batch`, `claim`, `load_ops`, `nlp_calls`, `save`, `map`.
- Роли ADMIN / EDITOR / READER, админка пользователей (`/api/admin/users`), настройки NLP (`/api/admin/nlp/*`).
- Индекс очереди `idx_nlp_task_open` (миграция `V9__nlp_task_open_index.sql`; проверить, что номер свободен).

## 2. Как запускать

Подготовка (один раз):
- Задать пароли до первого старта: `AVP_ADMIN_PASSWORD`, `AVP_EDITOR_PASSWORD`, `AVP_READER_PASSWORD`.
- Поднять PostgreSQL, Prometheus, Grafana (`docker compose up -d`, порты Grafana/Prometheus — по compose-файлу).
- Запустить `nlp-service` (FastAPI).
- Запустить backend: `cd backend; mvn spring-boot:run -Dspring-boot.run.profiles=demo`
  (число операций: `DEMO_OPERATIONS=N`; справочник 1M договоров / 300k клиентов генерируется один раз, если таблица `contracts` пуста).

Замер нагрузки (из `nlp-service`):
```
$env:AVP_RUN_QUERY="maxSeconds=1800"
python eval/run_load.py x10 120000      # метка, число операций С УЧЁТОМ хаоса (x10 = 100000 + 20000)
python eval/summarize_load.py x10       # точность по сценариям и хаосу
python eval/prom_timeline.py 1          # rps и латентность /classify по минутам за последний час
python eval/stage_timeline.py x10 <start_unix> <end_unix>   # мс на вызов по стадиям, по минутам
```
Результаты: `nlp-service/eval/load/<label>.json`.
`run_load.py` печатает `CHECK FAILED`, если справочник не равен ожидаемому (`AVP_EXPECTED_CONTRACTS`), intake не совпал с числом операций или прогон упёрся в таймаут. Тогда замер недействителен.

Смена объёма: остановить Java → `TRUNCATE operations CASCADE;` → запустить с новым `DEMO_OPERATIONS`.
Полный сброс: `TRUNCATE operations, contracts, clients CASCADE;`.

Проверки: `eval/check_security.py`, `eval/check_users_api.py` (`unknown id` в скрипте ожидает 409, реально 404 — скрипт неточен), `eval/check_nlp_admin_api.py`, тесты `mvn test`, `pytest` в `nlp-service`.

## 3. Результаты (чистая база: 1M договоров, порог NLP 0,5, Security включён, одна машина)

| | x1 | x2 | x3 | x10 | x10 (после индекса) |
|---|---|---|---|---|---|
| операций (с хаосом) | 12 000 | 24 000 | 36 000 | 120 000 | 120 000 |
| время прогона, с | 40,0 | 86,6 | 144,1 | 806,1 | 816,2 |
| операций в секунду | 300 | 277 | 250 | 149 | 147 |
| точность | 95,2% | 95,2% | 95,1% | 95,0% | 95,0% |
| хаос-сценарии верно | 2000/2000 | 4000/4000 | 6000/6000 | 20000/20000 | 20000/20000 |
| ошибочный AUTO | 0 | 0 | 0 | 0 | 0 |
| память Java, макс, МБ | 161 | 287 | 269 | 638 | 424 |
| CPU Java, макс | 10% | 11% | 11% | 15% | 9% |

- Маппинг линеен: ≈1300–1450 операций/с на любом объёме.
- Скорость всего конвейера падает с ростом объёма (300 → 149 оп/с).
- Наш x10 = 100 000 операций = ориентир «сутки банка» (~100k/день). На этом стенде это ≈11–14 минут. Это измерение, а не прогноз для прода (одна машина, синтетические данные, объём «1 млн» не измерялся).
- Точность по сценариям (x10): `THIRD_PARTY_NAME` 4973/10000 (49,7%); `THIRD_PARTY_NUMBER` 9999/10000; остальные 100%. Низкая цифра `THIRD_PARTY_NAME`: две причины — порог 0,75 и обработка имён (женские фамилии в именительном падеже, «ё»); при пороге 0,5 лучше, но это trade-off с ложными срабатываниями.
- Генератор содержит явные маркеры третьего лица, поэтому сравнение «ИИ лучше regex» на этих данных некорректно, не используем.

## 4. Где уходит время на x10 (816 с)

| Стадия | с | доля |
|---|---|---|
| `intake` (постановка в очередь) | 122,5 | 15% |
| `claim` (взять задачи) | 122,8 | 15% |
| `save` (запись результатов) | 155,4 | 19% |
| накладные `map` (`map` минус `mappingMillis`) | 121,7 | 15% |
| `load_ops` | 15,1 | 2% |
| вызовы Python `/classify` (`nlp_calls`) | 185,8 | 23% |
| сам маппинг | 92,6 | 11% |

- Внешние стадии (`intake` + `nlp_batch` + `map`) = 816,2 с, то есть полностью `run_s`; вне таймеров потерь нет.
- Работа с БД ≈ 537 с (66%). Python занят 23% времени и не является узким местом.
- Стадию `run_s − mappingMillis` раньше называли «NLP-стадией». Это неточно: туда входят очередь, БД и запись.
- Итераций конвейера (по 50 задач) на x10 2400. Стоимость итерации (131 / 145 / 166 / 301 мс на x1/x2/x3/x10) растёт с размером таблиц.

## 5. Что проверено и опровергнуто

- Гипотеза «`claim()` — основная причина»: до индекса запрос перебирал все готовые задачи (≈160 млн лишних чтений за 4 прогона; 40 мс и 38 006 буферов на вызов при 120k задач). Индекс убрал эти чтения (подтверждено статистикой индексов), общее время не изменилось (806 → 816 с). Гипотеза опровергнута; предсказания 400 и 750 с оказались неверными.
- Гипотеза «накопление состояния в Python»: латентность `/classify` 5–7 мс (в одну минуту до 11 мс) и не растёт вместе с падением скорости. Не подтверждена. Память Python не измерена (метрика не найдена, неверный `job`).
- Первый замер x2/x3/x10 недействителен: справочник дублировался при перезапуске (1M → 4M договоров). Исправлено (условие `contracts == 0`), замеры повторены.
- Разброс между прогонами не измерен (один прогон на метку). Разницу в 1–3% не интерпретировать.

## 6. Хаос-данные: промахи

- В `PARTIAL_NAME_ONLY` и `NOISY_NUMBER_WITH_PARTY` на x10 нужный договор не попал в кандидаты в 34 и 31 случае из 5000 (0,68% / 0,62%).
- Все 65 промахов приходятся на операции, у которых сохранено ровно 10 кандидатов (`maxStoredCandidates = 10`); при ≤ 9 промахов нет (0 из 9020). Среди 980 операций с `stored = 10` промах у 65 (6,6%). Это сильный признак причины, но лимит не менялся и перемер не делался.
- Влияние: оператор в очереди ручного разбора не видит нужный договор; система не угадывает, ошибочного AUTO нет.

## 7. Открытые вопросы (для следующего этапа)

1. **Скорость на больших объёмах.** Первым делом проверить гипотезу про мёртвые версии строк: во время прогона (мин. 8–10) выполнить SQL из `docs/load-testing.md#проверка` (n_dead_tup, backend_xmin, EXPLAIN запроса intake на пустом PENDING). Подтвердится — настроить autovacuum на `operations` и `nlp_task` либо убрать долгую транзакцию, затем один перепрогон x10 (120000). Не подтвердится — смотреть CPU Postgres, WAL/checkpoint, `NlpTaskWorker.saveSuccesses`, `batchSize` 50 → 500, `pg_stat_statements`.
2. **`maxStoredCandidates`** (раздел 6): решение за второго бэка. Если поднять (например, до 20), перемерить x1 (хаос-метрика).
3. **Индексы `idx_nlp_task_ready` и `idx_nlp_task_locked`** после `idx_nlp_task_open`, вероятно, лишние (первый читал 34 млн записей за 826 сканов), решение за вторым бэком.
4. **Метрика памяти Python** (`py_rss_mb`) пустая: проверить лейбл `job` в `prom_timeline.py`.
5. **Аномалия x1:** на прежней базе 94,5% (`THIRD_PARTY_NAME` 452/1000), на чистой 95,2% (519/1000). Причина не установлена (настройки NLP менялись, версия 9).
6. **Неизвестный итог на «1 млн операций»:** не измерялся, экстраполировать нельзя, пока причина падения скорости не найдена.
7. Мультипроцессный запуск Python потребует `PROMETHEUS_MULTIPROC_DIR`.
8. `/actuator/prometheus` открыт по CIDR (loopback и приватные сети); для прода нужен basic-auth.
9. Матрица прав временная (`RolePermissions`), ждёт аналитика.

## 8. Ограничения NLP (из eval)

- Размечено одним человеком, независимой проверки нет; наборы «засвечены», правила гибрида (B) в боевой код не переносились.
- Известные слабые места: ложный `NEGATED` на «за третье лицо, НДС не облагается»; при `extractedName == null` платёж идёт по контрагенту и при одном договоре возможен AUTO (зона `MappingDecider`).
- Нечёткого поиска по номеру договора нет; «фамилия + инициалы» и сценарий для счетов исключены из спринта.
